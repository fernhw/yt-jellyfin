GYRA — Scaling Architecture

How we go from one Mac mini to 3,000 teams without rewriting the world.
Plan first, scale later. The current stack handles the next 50 paying teams without changes. We design the destination now, then migrate incrementally, only when real traffic forces us. Every step ships on its own and is reversible.

The core decision: shard by team, stay in Python

We do not rewrite to Elixir, Go, or anything we don't already operate. The team building this is one person who knows Python and Flask. The right architecture is the one we can keep running at 3 AM \u2014 not the one with the best benchmarks.

Architecture in one sentence: each team lives in its own SQLite file, multiple teams share an instance, multiple instances are picked by a dumb router that maps team_slug \u2192 instance_url. Scaling = add an instance, move some teams to it. No new tech.

The two key ideas

1. One SQLite file per team \u2014 not a shared database

  • data/teams/acme.db, data/teams/bolt.db, etc.
  • Strongest possible silo: file-level isolation. Code that opens acme.db physically cannot read bolt.db. No row-level security, no WHERE team_id = ? bugs, no leakage ever possible.
  • Backup a team = cp acme.db backups/
  • Delete a team (GDPR request) = rm acme.db
  • Move team to another instance = scp acme.db newhost: + update router
  • SQLite in WAL mode handles 500 users + ~100 concurrent writes comfortably. We will never get near that per team.

2. The router is dumb and stateless

  • Nginx (or a tiny Flask app) reads team_slug from subdomain or URL prefix
  • Looks it up in a small registry (JSON file or a tiny SQLite): {"acme": "https://inst1.gyra.app"}
  • Proxies HTTP and WebSocket to that instance
  • That's the entire job. No business logic, no team data, no auth decisions.

The phased rollout

Each phase ships independently and is reversible. We do not move to phase N+1 until phase N hurts.

Phase 0 \u2014 Today One box, one DB, no sharding

Mac mini, Flask, single gyra.db, cloudflared tunnel. This is fine. No code changes.

Holds: ~50 active paying teams comfortably. Probably more if traffic is light.

Trigger to move on: 30 paying teams or CPU sustained >60% during planning hours or first user complaint about lag.

Phase 1 \u2014 Team-slug routing in code

Add /t/<team_slug>/... to all URLs. Middleware sets g.team_slug. Single DB still, but every query is namespaced by team. Zero infrastructure changes \u2014 this is a code-only refactor on the existing Mac mini.

Why now even though Phase 0 holds: the URL shape needs to exist before we shard. We bake it in early so every new route uses it from day one. Far cheaper than retrofitting.

Effort: 1\u20132 weekends. Mostly find-and-replace in the routes and templates.

Trigger: next time we touch the routes layer for any reason, do this in the same pass.

Phase 2 \u2014 Per-team SQLite files

Switch get_db() to get_db(team_slug) returning a connection to data/teams/<slug>.db. Each team gets a fresh DB created from the schema on first signup. Still one instance.

This is the big win. File-level silo is in place. Backups become per-team. Self-host becomes trivial. Everything else stays the same.

Effort: 1 week. Touches db.py, schema migrations need a per-file runner, signup creates the file.

Trigger: first paying customer who asks "where exactly is my data stored?" \u2014 or, defensively, before we hit 20 paying teams.

Phase 3 \u2014 Router + second instance

Write a tiny Flask router (50 lines) that reads team_slug and proxies to the right instance. Spin up a second instance on the same Mac mini (different port) or on a cheap Hetzner box. Move half the teams over. Validates the model before it has to scale.

Effort: 1\u20132 weeks. Router itself is trivial; the work is in deployment automation and the per-team registry.

Trigger: 40 paying teams or Mac mini at 80% CPU peak or first paying Self-host customer (their box becomes a real "instance" you need a router for).

Phase 4 \u2014 Cloud, multi-region, auto-deploy

Move off the Mac mini. Hetzner cluster, Docker image per instance, GitHub Actions to deploy, registry in a managed Postgres. Optional: separate EU and US instance pools for data residency. SSO becomes real.

Effort: 3\u20134 weeks of focused work, mostly DevOps.

Trigger: 200 paying teams or first enterprise/Publisher customer asking about uptime SLA, data residency, or compliance.

Sockets: why this design dodges the hardest scaling problem

Real-time collaboration is normally the thing that forces a Redis pub/sub layer, sticky sessions, and a lot of operational complexity. Our shard model eliminates that need entirely:

  • A team's users always land on the same instance (router guarantees it)
  • Flask-SocketIO with eventlet handles 2k\u20135k concurrent sockets per instance easily
  • Rooms are scoped to the team: socketio.emit('board:update', data, room=f'team_{slug}')
  • No Redis needed. No cross-instance pub/sub. No sticky-session headaches.
This is the architectural prize. Sharding by team gives us realtime sockets for free because the silo boundary is the broadcast boundary.

Trade-offs (honest)

CostMitigation
Cross-team analytics need an aggregator Nightly cron opens every DB, sums into one analytics DB. Runs in seconds for 3,000 small SQLite files.
Schema migrations run per-file Single script: for f in data/teams/*.db: apply(f). Parallelised, completes in minutes.
A team outgrowing 500 users must move to its own instance This is good: those are Publisher / Self-host customers and can pay for dedicated iron.
One instance going down takes 40 teams with it Acceptable blast radius. Far better than "one DB outage kills 3,000 teams." Instance restarts in seconds.
Router becomes a single point of failure Run two routers behind a cheap load balancer once we have >200 teams. Until then, a 50-line Flask app on the Mac mini is fine.

What we are explicitly NOT doing

  • No Elixir / Go / Rust rewrite. We don't know them. We can't operate them at 3 AM. End of discussion.
  • No Postgres migration before Phase 2. SQLite per-team is genuinely simpler and faster for our access pattern. Postgres comes in only as the registry/analytics DB later.
  • No Kubernetes. Docker + systemd + nginx is enough until 1,000+ teams.
  • No Redis until proven necessary. The shard model is designed precisely to avoid it.
  • No microservices. One Flask app per instance, period. Modular code, monolithic deploy.

What we do RIGHT NOW

Nothing infrastructural. Phase 0 is fine.

The only thing to bake in today is the discipline that every new feature is written team-scoped from day one: every query joins on team, every URL carries the slug, every socket emits to a team room. That way Phase 1 and Phase 2 are pure refactors, never re-architecture.

Build like it's already sharded. Deploy like it isn't, until it has to be.

Open questions

  • Subdomain (acme.gyra.app) or URL prefix (gyra.app/t/acme)? Subdomains are cleaner for cookies and tenant isolation; prefix is simpler for SSL and dev. Lean: subdomain, but ship prefix first.
  • Where does shared user identity live? (One person on multiple teams.) Probably a separate identity.db the router consults for auth before proxying. Needs design.
  • Where do user-uploaded images live? Per-team folder on disk (mirrors the DB shard model) vs. S3-compatible blob store. Lean: per-team folder until Phase 4, then S3.
  • How do we expose Self-host? Same Docker image as a production instance, with the router baked in pointing at localhost. The customer runs one container, gets the full GYRA on their own iron.
